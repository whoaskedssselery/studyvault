# Frontend StudyVault

Два режима: учебная библиотека на фейковых данных и отдельный кабинет для реальных аккаунтов Go API. Начальная демобиблиотека читается HTTP-запросом из `frontend/public/mock.json`, действия сохраняются в localStorage. Её вход и регистрация имитируются; для демонстрации используйте вымышленные данные. В «Кабинете API» работают настоящие запросы к серверу.

## Запустить исходники

Нужен Node.js 20.19+ или 22.12+.

```powershell
cd D:\spo2\studyvault\frontend
npm ci
npm run dev
```

Обычно открывается http://127.0.0.1:5173. После первых действий начальные материалы берутся из сохранённой локальной копии, поэтому изменение mock.json не заменяет ваши публикации автоматически.

## Файлы по заданию

`deliverables/frontend/index.html` содержит собранные React, CSS и JavaScript. Соседний `mock.json` — отдельные фейковые данные. Эти два файла можно передать тимлиду и разместить на статическом HTTP-хостинге. В этой сборке навигация через `#/…`, поэтому дополнительная настройка SPA-маршрутов на хостинге не требуется. `serve.mjs` — необязательный локальный сервер, подробности в [инструкции комплекта](../deliverables/frontend/README.md).

```powershell
cd D:\spo2\studyvault
node deliverables/frontend/serve.mjs
```

Открыть http://127.0.0.1:4173/. Через `file://` браузеры ограничивают fetch локального JSON; показывается сообщение с предложением открыть HTTP-сервер.

## Проверки и пересборка

```powershell
cd frontend
npx playwright install chromium
npm run package:submission    # TypeScript, production-сборка, обновление сдаваемых файлов
npm test                     # UI, загрузка JSON, экспорт, API-ответы, сборка, mobile
npm run test:proxy           # HTTP-прокси: JSON, cookie, заголовки и курсоры
npm run api:generate         # типы из актуального backend/api/openapi.yaml
```

Серверы тестов работают на 5173 и 4174. Изолированные браузерные контексты не меняют данные открытого пользовательского браузера. Снимки прошлого этапа обновляются в `docs/screenshots/`, снимки сдаваемой сборки — в `docs/assignment-2/screenshots/`. Там же сохраняется фактический результат проверки доступности локального API.

## Реализованные сценарии

- Библиотека: поиск по названию, содержимому и тегам, предметы, семестры, тип материала, сортировка, карточки/список.
- Чтение конспекта, комментарии, оценки 1–5, избранное.
- Tiptap: заголовки, полужирный, курсив, списки, блоки кода. Создание, сохранение и повторное редактирование черновиков.
- Отправка на проверку, одобрение и отклонение с причиной. Отредактированный материал проходит модерацию заново.
- Скачивание материала в Markdown. Подтверждаемое удаление собственного локального материала.
- PDF/PNG/JPEG/WebP: до 2 МБ на файл, не более 3 файлов. Файлы доступны для скачивания. Квота localStorage ограничена; при переполнении сохранение не считается успешным.
- Демовход, регистрация, профиль, рейтинг и модерация. Демоаккаунт Алексея открыт по умолчанию; после выхода — кнопка «Войти в демо».
- Ctrl+K / Cmd+K, мобильное меню, пустые состояния, ошибки JSON и повторная загрузка.
- Отдельная диагностика API: HTTP-статусы, проверка Content-Type и JSON-формата, сохранение результатов в файл.

## Что изменилось на сервере

Основа перепроверена 14 октября 2026 по main `bfcf9ae`. В бэкенде реализованы Docker Compose, миграции, Go-сервер, Swagger UI, health check, регистрация/вход/refresh/logout, CRUD предметов и заметок, теги, Meilisearch, S3-вложения, обратные ссылки и граф. Добавлены CORS, rate limit, безопасные cookie и CI. Контракт — `backend/api/openapi.yaml`; типы генерируются в `frontend/src/api/schema.d.ts`. Снятые бэкендером скриншоты и его описание сохранены в README и docs/screenshots.

Контракт API и демомодель фронтенда **различаются**. На сервере материалы и предметы принадлежат пользователю; общая библиотека, комментарии, рейтинг и модерация пока демонстрационные.

| Данные фронтенда | Серверный контракт |
| --- | --- |
| `User.name` | `User.display_name` |
| `Note.subject` — название | `Note.subject_id` — UUID; название из `/subjects` |
| `Note.content` | TiptapDoc в `content` |
| `Note.tags` — строки | `tags` — массив объектов `{id, name}` |
| `Note.createdAt` | `created_at`, дополнительно `updated_at` |
| `saves`, `ratings`, `comments`, `status`, `views` | В текущем Note-контракте этих полей нет |

Подмена mock.json ответом `/notes` не сработает, поскольку список заметок не содержит content, users и демонстрационные поля. Поэтому API-кабинет использует серверные модели напрямую, отдельные TanStack Query-ключи и клиент openapi-fetch. Общие материалы и социальные функции остаются в демонстрационном режиме; серверная реализация требует согласования. Документация API в `.docx` остаётся вкладом аналитика.

## Кабинет API

Откройте `/workspace` или `#/workspace` в сдаваемом HTML. Вкладки демоверсии продолжат работать без сервера.

Для сервера из корня проекта: скопируйте `.env.example` в `.env`, задайте свои значения и выполните `docker compose --profile app up -d --build`. Подробный порядок — в корневом README. В кабинете создайте аккаунт или войдите в существующий аккаунт Go API.

Работают: реальный вход/регистрация/выход; создание предмета; список заметок с курсором и фильтрами; создание, изменение, закрепление и удаление заметки; Tiptap JSON; поиск с безопасной подсветкой; создание и назначение тегов; граф и обратные ссылки; регистрация и прямая PUT-загрузка вложения в S3, скачивание и удаление файла.

Access-токен хранится только в памяти. В sessionStorage сохраняется информация о пользователе без токена. После reload клиент использует refresh-cookie; одновременные 401 объединяются в одно обновление. После невалидного refresh личные данные и query-кэш очищаются. Неправильный пароль не вызывает refresh, 429 показывает Retry-After. Пароль ограничен 72 байтами согласно контракту.

Vite и serve.mjs переписывают Path refresh-cookie с `/auth` на `/backend-api/auth`. Для локального HTTP серверу нужен `COOKIE_SECURE=false`, как в текущем примере бэкенда. В S3-запрос не попадает Bearer-токен. При ошибке PUT запись файла не маскируется как успешная загрузка; доступна повторная попытка. Для прямой загрузки хранилище должно разрешать origin фронтенда в CORS.

В переносимой сборке без serve.mjs или другого прокси API-кабинет не сможет обращаться к серверу; демоверсия останется рабочей. Для реального API на статическом хостинге настройте маршрут `/backend-api` к своему серверу и HTTPS/cookie согласно корневому README.

## Диагностика JSON

Откройте `/api-status` в режиме разработки или `#/api-status` в сдаваемой сборке. Кнопка проверяет:

- `GET /health` → 200 и `{"status":"ok"}`; 503 означает недоступную БД.
- `GET /notes`, `GET /subjects` без Bearer-токена → 401 и JSON-ошибка `error.code` / `error.message`.

Это не проверка CRUD и не авторизация демоаккаунта на сервере. Запросы идут через `/backend-api`, который проксируется на `http://127.0.0.1:8080`. В Vite адрес можно изменить в `.env.local` по образцу `frontend/.env.example`; для готового `serve.mjs` — переменной окружения `STUDYVAULT_API_TARGET`. Секреты и токены не записываются в отчёт.

## Ограничения

В учебной библиотеке роль модератора, комментарии, рейтинги и просмотры демонстрационные. Серверный кабинет работает с персональными заметками и не переносит демоматериалы в аккаунт автоматически. В UI пока нет изменения/удаления предметов и удаления тега целиком; сервер поддерживает эти методы. Bundle включает редактор; перед production-развёртыванием стоит разделить страницы ленивой загрузкой.

На этой машине Docker daemon не запущен, поэтому энд-ту-энд проверка с реальными Postgres/Meilisearch/S3 не выполнена. Клиент проверен в браузере на подставленных HTTP-ответах актуального контракта. Проверки бэкендера на реальных сервисах доступны в его README и CI; они не подменяются результатами фронтенд-тестов.

Для сброса удалите ключи `studyvault.database.v1` и `studyvault.session.v1` через DevTools. Это удалит ваши локальные демоаккаунты, публикации и вложения.
