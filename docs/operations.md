# Эксплуатация

Инструкция по вводу в действие (раздел 8 ТЗ) и по обслуживанию. Все команды выполняются из корня репозитория.

## 1. Первый запуск

```bash
cp .env.example .env          # задайте свои значения (см. ниже)
docker compose --profile app up -d --build
```

Поднимутся PostgreSQL, Meilisearch, S3-хранилище, миграции на пустой базе и API. Проверка: `curl http://localhost:8080/health`
должен вернуть `{"status":"ok"}`.

В `.env` обязательно поменять:

| Переменная | Что поставить |
|---|---|
| `POSTGRES_PASSWORD`, `MEILI_MASTER_KEY`, `S3_SECRET_KEY` | свои длинные случайные значения |
| `JWT_SECRET` | не короче 32 случайных символов |
| `COOKIE_SECURE` | `true` (или убрать): refresh-cookie должна уходить только по HTTPS |
| `CORS_ORIGINS` | адрес веб-клиента, только явные адреса, без `*` |
| `SEED_PASSWORD` | в продакшене пустым: команда `seed` предназначена только для показа |

Секреты лежат только в `.env`. Он в `.gitignore`, в клиентский код и в логи не попадает.

## 2. Модератор

Через API роль не назначить, так задумано. Зарегистрируйте будущего модератора обычным способом, затем:

```bash
docker compose --profile app run --rm --entrypoint /promote api moderator@example.com
```

Вернуть обычную роль: добавить в конце `student`. Роль проверяется по базе при каждом запросе, поэтому понижение
действует сразу.

Для показа можно наполнить стенд демо-данными: `docker compose --profile app run --rm --entrypoint /seed api`.

## 3. HTTPS, публичная ссылка и почта

Боевой стенд описан в [deploy/](../deploy): к обычному стеку добавляется Caddy с автоматическими сертификатами Let's Encrypt,
API наружу не публикуется и доступен только через него, а веб-клиент отдаётся с того же адреса.

Что нужно: домен, A-запись которого указывает на сервер, открытые порты 80 и 443, каталог со сборкой клиента и настоящий
SMTP-сервер (для писем со ссылками сброса пароля и подтверждения почты). В `.env`:

```
DOMAIN=studyvault.example.com
FRONTEND_DIR=./deliverables/frontend     # каталог со сборкой клиента
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USERNAME=...
SMTP_PASSWORD=...
SMTP_FROM=StudyVault <no-reply@example.com>
PASSWORD_RESET_URL=https://studyvault.example.com/reset-password   # страница клиента, куда ведёт ссылка из письма
EMAIL_VERIFY_URL=https://studyvault.example.com/verify-email        # необязательно: по умолчанию /verify-email на том же сайте
COOKIE_SECURE=true
```

Запуск:

```bash
docker compose -f docker-compose.yml -f deploy/docker-compose.prod.yml --profile app up -d --build
```

Проверено локально с доменом `localhost`: HTTPS работает, `http://` перенаправляет на `https://` (308), прямой порт API
закрыт, документация и клиент отдаются с одного адреса, `Strict-Transport-Security` выставляется.

**Лимит попыток входа за прокси.** API считает попытки по адресу клиента. За прокси соединение приходит с адреса прокси,
поэтому ему разрешено доверять `X-Forwarded-For` (`TRUSTED_PROXIES`, в боевом файле это внутренние сети Docker). Из заголовка берётся
первый справа адрес, не принадлежащий доверенному прокси: Caddy сам дописывает настоящий адрес клиента, а подделанное клиентом
слева значение лимит не сбрасывает (проверено: попытки с разными поддельными адресами упёрлись в 429). Без `TRUSTED_PROXIES`
заголовок игнорируется целиком. Не указывайте широкие сети вроде `0.0.0.0/0`: такое значение сервер не примет.

**Почта.** Без `SMTP_HOST` сброс пароля отвечает 503 `email_unavailable`, остальное API работает, а подтверждения почты нет совсем:
новые аккаунты считаются подтверждёнными сразу, иначе они никогда не смогли бы публиковать. С почтой регистрация отправляет письмо со ссылкой
(`EMAIL_VERIFY_URL`, действует 24 часа, работает один раз), и до подтверждения нельзя публиковать материалы, комментировать и оценивать
(403 `email_not_verified`); читать, вести личные заметки и собирать избранное можно. Аккаунты, созданные до появления подтверждения, считаются
подтверждёнными. Открытая ссылка сброса пароля тоже подтверждает адрес: письмо дошло до владельца. Локально письма ловит
Mailpit (окно `http://localhost:8025`), отдельной настройки не нужно: ссылка из письма ведёт на `PASSWORD_RESET_URL`.
Письмо уходит в фоне, поэтому по скорости ответа нельзя узнать, есть ли аккаунт с такой почтой.

Ссылки на загрузку и скачивание файлов ведут на S3. Задайте `S3_PUBLIC_ENDPOINT` (и `S3_USE_SSL=true`) так, чтобы браузер
пользователя мог открыть этот адрес: для боевого стенда это отдельный поддомен хранилища за своим TLS.

## 4. Закрыть административные интерфейсы

Порты базы, поиска и хранилища уже привязаны к `127.0.0.1`, так что снаружи они недоступны. Не меняйте это на `0.0.0.0`.
Консоль S3 (порт 9001) нужна только администратору: на публичном сервере её лучше не публиковать вовсе и открывать
через SSH-туннель (`ssh -L 9001:127.0.0.1:9001 сервер`). Брандмауэр сервера должен пропускать снаружи только 80 и 443.

## 5. Резервное копирование

Ежедневная копия базы и файлов:

```bash
bash scripts/backup.sh /var/backups/studyvault
```

Скрипт делает дамп PostgreSQL (`pg_dump -Fc`) и архив тома с файлами, пишет их под временным именем и переименовывает,
когда копия готова, а старше `KEEP_DAYS` (14) суток копии удаляет. Расписание (cron, раз в сутки в 03:15):

```
15 3 * * *  cd /srv/studyvault && bash scripts/backup.sh /var/backups/studyvault >> /var/log/studyvault-backup.log 2>&1
```

Копии стоит регулярно вывозить с самого сервера: копия на том же диске не переживёт потерю диска.

## 6. Проверка восстановления

Копия, которую ни разу не восстанавливали, копией не считается. Раз в неделю и после любого изменения схемы:

```bash
bash scripts/restore-check.sh                       # самый свежий дамп из ./backups
bash scripts/restore-check.sh /var/backups/studyvault/studyvault-db-….dump
```

Скрипт восстанавливает дамп во временную базу `studyvault_restore_check` (рабочую не трогает), сверяет число строк
по ключевым таблицам и версию миграций с рабочей базой, проверяет, что представление библиотеки читается, и удаляет
временную базу. Код возврата 0 значит, что копия пригодна. Обрезанный или битый дамп он отвергает (проверено).

Восстановление в боевую базу, когда она потеряна:

```bash
docker compose --profile app stop api
docker compose exec -T postgres psql -U "$POSTGRES_USER" -d postgres -c "DROP DATABASE IF EXISTS $POSTGRES_DB" \
  -c "CREATE DATABASE $POSTGRES_DB"
docker compose exec -T postgres pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner --exit-on-error < studyvault-db-….dump
# файлы: распаковать архив в том S3
docker run --rm --volumes-from "$(docker compose ps -q s3)" -v "$PWD/backups:/backup" alpine tar -xzf /backup/studyvault-files-….tar.gz -C /data
docker compose --profile app up -d
docker compose --profile app run --rm --entrypoint /reindex api     # пересобрать поисковый индекс из базы
```

Поисковый индекс не бэкапится: он воспроизводится из PostgreSQL командой `reindex`.

## 7. Проверки после перезапуска и под нагрузкой

```bash
bash scripts/restart-check.sh     # публикует материал с файлом, перезапускает сервисы стека, проверяет данные (N3)
bash scripts/loadtest.sh          # 1000 материалов, 20 пользователей, p95 списка не более 2 с (N3)
```

Результаты прогона 14 октября 2026 на машине разработчика (PostgreSQL, Meilisearch и S3 в Docker на одном хосте):

| Проверка | Цель по ТЗ | Результат |
|---|---|---|
| `GET /health` после перезапуска, повторное открытие опубликованного материала, файл, поиск | доступны | все четыре проверки пройдены |
| Список библиотеки, 1010 материалов, 20 одновременных пользователей, 500 запросов (все сортировки и фильтры) | p95 не более 2000 мс | p50 20 мс, p95 40 мс, p99 50 мс, ошибок нет |

Скрипт `loadtest.sh` создаёт временные данные с меткой и удаляет их по завершении.

## 8. Журналы и диагностика

Журнал в JSON, одна строка на запрос, без query string и заголовков. Клиенту в каждом ответе приходит `X-Request-ID`:
по нему строка находится командой `docker compose logs api | grep <id>`. Уровень и формат: `LOG_LEVEL`, `LOG_FORMAT`.
Если Meilisearch или S3 недоступны, остальное API продолжает работать (поиск и файлы отвечают 503).

## 9. Обновление

```bash
git pull
docker compose --profile app up -d --build     # новые миграции применяются сами сервисом migrate
```

Перед обновлением, меняющим схему, сделайте копию (`scripts/backup.sh`). Контракт API версионируется в пути
(`/v1`), несовместимые изменения выходят под `/v2`.
